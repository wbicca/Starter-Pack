# Starter Pack v1.2 — Verificação determinística de batch

**Data:** 2026-07-10 · **Status:** escopo aprovado pelo humano (itens 1-3+5 da análise
de qualidade de entrega) · **Alvo:** template v1.2.0

## Problema

O código entregue é testado **por disciplina, não por mecanismo**:
1. O `quality-gate` roda só comandos configurados no `docs/STACK.md`; com `Test: TBD`
   (início de todo projeto), o batch passa sem nenhum teste executado.
2. O gate pode aceitar o auto-relato do subagente ("8/8 passing") em vez de evidência
   própria.
3. A execução dos comandos pelo gate é improvisada pelo modelo (várias idas e vindas,
   tokens) em vez de um trilho determinístico.
4. Projetos derivados nascem **sem CI próprio** — o `ci.yml` do template protege só o
   starter em si.

Fora de escopo (decisão explícita do humano): validação de runtime por batch
(cara demais como gate obrigatório — vai para o `release-sanity`/sob demanda em ciclo
futuro), pre-push hook, smoke no Windows.

## Seção 1 — `scripts/quality/batch-verify.mjs` (novo)

Script determinístico, irmão do `quick-check`. Responsabilidade: **executar os comandos
de qualidade configurados e devolver evidência** (exit code + tabela em stderr).

### Comportamento
1. Lê `docs/STACK.md`: tabela **Commands** (Lint, Typecheck, Test, Build — nesta
   ordem; **Format é excluído de propósito** — formatadores mutam arquivos e um
   verificador nunca muta) e o campo **Profile**.
2. Executa **apenas** comandos com Status `CONFIGURED` (nunca inventa; `TBD`/
   `UNCONFIGURED` são reportados como *not configured*). Para na primeira falha
   (fail-fast), reporta as demais como *skipped*.
3. **Política de Test não configurado** (só quando o diff do batch toca código de
   aplicação — mesma heurística de extensões do write-guard):
   - Profile `standard` → **exit 2** (bloqueia): "Test command UNCONFIGURED and the
     batch touches app code — configure it in docs/STACK.md, or rerun with
     `--accept-unconfigured` (decisão humana; registre no DELIVERY_LOG)".
   - Profile `light` → **warning**, não bloqueia.
   - Flag `--accept-unconfigured` rebaixa o exit 2 para warning (waiver explícito).
4. **Sinal código-sem-teste** (item 5): se o diff tem mudanças em código de aplicação
   e nenhuma mudança em arquivos de teste (heurística: `*.test.*`, `*.spec.*`,
   `__tests__/`, `test/`, `tests/`, `e2e/`), emite **warning** — nunca bloqueia
   (review signal, filosofia do ENGINEERING_STANDARDS).
5. Diff do batch: `git diff HEAD` + staged + untracked não-ignorados (mesma base do
   quick-check); flag `--range <ref>` opcional para verificar um intervalo (uso em CI:
   `--range origin/master`).
6. Saída: tabela `Command · Result · Status` em stderr (formato do deliverable do
   quality-gate) + linha final `batch-verify: PASS | FAIL | PASS-WITH-WARNINGS`.
   Exit codes: `0` pass (com ou sem warnings) · `1` comando configurado falhou ·
   `2` bloqueio por Test não configurado (standard).
7. Fail-safe: STACK.md ausente/ilegível → trata como tudo não configurado; sem git →
   roda comandos configurados mas pula as heurísticas de diff (warning explicando).
8. Zero dependências (node builtins), timeout por comando (default 10 min),
   `stdio: inherit` para o humano ver a saída real dos testes.

### Verificação do próprio script
`scripts/quality/batch-verify-smoke.mjs`: fixtures em temp dir (STACK.md fake com
comandos `node -e "process.exit(0|1)"`), casos: tudo configurado e verde → 0 · Test
falhando → 1 · Test TBD + diff de app + standard → 2 · idem + light → 0 com warning ·
idem + `--accept-unconfigured` → 0 · src mudado sem teste → warning · STACK ausente →
não explode. Entra no `ci.yml` do template (ubuntu; Windows coberto pelo doctor).

## Seção 2 — `quality-gate` endurecido (evidência > alegação)

`.claude/skills/quality-gate/SKILL.md`:
- Step 1 passa a ser: **rodar `node scripts/quality/batch-verify.mjs`** e reportar a
  tabela/exit code — o gate não improvisa mais comandos um a um.
- Regra nova: **o resultado do batch-verify é a única evidência aceita** para "checks
  passed" — o relato do subagente nunca substitui a execução pelo gate.
- Exit 2 (Test não configurado, standard): o gate **FALHA** e apresenta as duas saídas
  ao humano (configurar o comando · waiver com registro no DELIVERY_LOG).
- O restante do gate (diff, secrets, design check, sanctioned-path, worktrees, review,
  delivery log) permanece como na v1.1.

  configurado · `node scripts/quality/batch-verify.mjs --range origin/<default-branch>`

  runtime à stack.

  a partir do template **quando** o projeto tem (ou terá) repositório remoto e comandos

  Item no checklist de validação.
- Mesmo trilho local e remoto: CI chama o mesmo `batch-verify.mjs`.

## Riscos e mitigação
- **Falso bloqueio em projeto sem testes por decisão** (site estático): waiver
  `--accept-unconfigured` + perfil light vira warning; a decisão fica registrada.
- **Comandos lentos** → timeout configurável por env (`BATCH_VERIFY_TIMEOUT_MS`),
  fail-fast.
- **Heurística de "arquivo de teste" errar** → é warning, nunca bloqueio.
- **Regressão** → batch-verify-smoke no CI do template.
