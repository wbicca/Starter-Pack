# Starter Pack v1.1 — Perfis, política de exposição e design standards

**Data:** 2026-07-09 · **Status:** aprovado pelo humano (design) · **Alvo:** template v1.1.0

## Problema

1. **Fricção de segurança desalinhada com o risco real.** Os hooks bloqueiam qualquer
   escrita em `.env` e qualquer segredo literal em qualquer arquivo — mesmo quando o
   arquivo é git-ignored e nunca chegaria ao GitHub. O risco real é **exposição**
   (entrar no commit / arquivo versionável), não existência local. Só o `quick-check`
   já segue o critério certo (bloqueia apenas `.env` *versionável*).
2. **Orquestração obrigatória até para tarefa de 1 linha.** O `orchestrator-write-guard`
   nega (DENY) toda escrita inline de código de aplicação na janela principal. Tarefas
   que o Claude Code resolveria sozinho exigem delegação ou sessão de manutenção.
3. **Design frontend sem contrato.** Existe `frontend-designer`, mas nenhum equivalente
   de `ENGINEERING_STANDARDS.md` para design, e nenhum item de design nos gates.

## Decisões (aprovadas pelo humano em 2026-07-09)

- Inline: **ASK global + perfil light** (light passa direto).
- `.env`/segredos: **política baseada em exposição total** (git-ignored passa; versionável bloqueia).
- Design: **standards doc + gate de design + agentes referenciam o doc**.
- Perfil light: **segurança sempre, gates proporcionais** (BMAD/review formal opt-in;
  fluxos sensíveis mantêm disciplina completa).
- Armazenamento do perfil: campo `Profile` em `docs/STACK.md` (opção recomendada; as
  alternativas — env var em `settings.local.json`, arquivo marcador — foram descartadas
  por tocarem governança ou criarem arquivo extra).

## Seção 1 — Perfis de projeto

### Campo
`docs/STACK.md` ganha, junto ao `Status`:

```
> **Profile: standard**  (allowed values: standard · light)
```

- Default do template: `standard`.
- `project-onboarding` classifica o **porte** (pergunta explícita ao humano: tarefa/projeto
  simples vs. produto completo) e grava o perfil.
- Trocar de perfil = editar a linha (docs/ é editável inline pela janela principal).
- Leitura pelo hook: regex `Profile:\s*(standard|light)` sobre `docs/STACK.md`;
  campo ausente/ilegível → assume `standard` (fail-safe conservador).

### Semântica
| Aspecto | `standard` | `light` |
|---|---|---|
| Escrita inline de código de app (janela principal, Write/Edit/Bash) | **ASK** (antes: DENY) | **passa direto** |
| Governança (`CLAUDE.md`, `AGENTS.md`, `.claude/**`, `.codex/**`, `.agents/**`, `scripts/quality/**`) | DENY (override→ASK) — inalterado | idem — **light não relaxa governança** |
| Hooks de segurança + quick-check | integrais | integrais |
| quality-gate por batch | completo (atual) | **resumido**: comandos configurados do STACK + inspeção de diff/segredos; sem review formal obrigatório |
| BMAD / planejamento formal | obrigatório p/ trabalho não-trivial (atual) | **opt-in** (só quando o humano pedir) |
| `requesting-code-review` por batch | obrigatório (atual) | opt-in, exceto fluxos sensíveis |
| Fluxos sensíveis (auth, RLS, pagamentos, PII, webhooks) | disciplina completa + `security-auditor` | **igual ao standard** — exceção dura, sem relaxamento |
| Delegação / worktrees / fan-out | caminho canônico p/ médio+ | disponíveis, opcionais |

### Mudanças no `orchestrator-write-guard.mjs`
- Nova função `readProfile(root)` (lê `docs/STACK.md`, cache por processo é
  desnecessário — hook é um processo por chamada).
- Main window + app code: `deny(REASON_APP)` → `standard`: `ask(REASON_APP_ASK)`;
  `light`: `pass()`.
- Novo reason code: `ORCHESTRATOR_WRITE_ASK: small-task inline write — approve to
  implement inline, or decline and delegate to an implementation agent.`
- `CLAUDE_ORCHESTRATOR_WRITE_OVERRIDE` continua existindo só para governança
  (semântica atual, inalterada).
- Política de subagentes, out-of-root e worktree-normalization: inalteradas.

## Seção 2 — Política de exposição (.env e segredos)

Critério único em todas as camadas de PreToolUse: **"pode entrar no commit?"**.

### Helper compartilhado
`.claude/hooks/lib/exposure.mjs` exportando `isVersionable(absPath, root)`:
- Versionável = **tracked** (`git ls-files --error-unmatch`) **ou não-ignorado**
  (`git check-ignore -q` retorna não-zero).
- Fail-safe: git ausente, erro, timeout, fora de repo → **versionável (bloqueia)**.
- Usado por `protect-sensitive-files`, `scan-secrets` e `block-dangerous-bash`
  (substitui os comentários "keep in sync" por import real).

### Comportamento por camada
| Camada | Regra nova |
|---|---|
| `protect-sensitive-files` | `.env`/`.env.*` real **ignorado e não-tracked** → pass silencioso. Versionável → DENY com mensagem acionável: "add it to .gitignore first, then retry". Templates (`.env.example` etc.) → pass (inalterado). |
| `scan-secrets` | Se o **arquivo-alvo** da escrita é ignorado e não-tracked → pass (sem scan). Caso contrário → comportamento atual integral. (O alvo vem de `tool_input.file_path`; escrita sem path identificável → scan normal.) |
| `block-dangerous-bash` §5 | Alvos `.env` de `>`/`tee`/`cp`/`mv`/`rsync`: mesma regra por exposição. Arquivos do contrato do starter (CLAUDE.md/AGENTS.md/CONSTITUTION): DENY inalterado. |
| `block-dangerous-bash` (novo) | `git add -f` / `git add --force` → **ASK** ("força arquivo ignorado para o índice — pode expor um segredo local"). Fecha a brecha que a política de exposição abre. |
| `quick-check` (Stop) | Inalterado — já é exposure-based e permanece a rede final. |

## Seção 3 — Design standards

- **`docs/DESIGN_STANDARDS.md`** (novo, stack-agnostic, mesma filosofia "review signal,
  not hard gate" do ENGINEERING_STANDARDS): hierarquia visual; escala de espaçamento
  consistente; tipografia (escala, pesos, line-height); cor e contraste (WCAG AA como
  piso); os **5 estados de toda view** (vazio, loading, erro, sucesso, parcial);
  feedback e microinterações; responsividade (mobile-first ou o padrão do projeto);
  dark mode quando o projeto o suporta; consistência de componentes (reusar antes de
  criar variante); motion com moderação e propósito.
- **`.claude/rules/design-quality.md`**: rule path-scoped (`**/*.{tsx,jsx,css,scss,vue,svelte,html}`)
  apontando para o doc (espelho do padrão `code-quality.md`).
- **Agentes**: `frontend-designer.md` e `frontend-engineer.md` passam a citar
  `docs/DESIGN_STANDARDS.md` como contrato de qualidade visual.
- **`quality-gate`** (skill): nova subseção condicional — *quando o batch toca arquivos
  frontend*, checar: estados cobertos · contraste/acessibilidade básica · responsividade ·
  consistência com a linguagem visual do projeto. Reporta como os demais itens.
- **Onboarding**: template do STACK.md ganha seção **Visual language** (referência de
  design, tokens/tema, biblioteca de componentes, ou `n/a` para projetos sem UI),
  preenchida no onboarding.
- **`docs/ENGINEERING_STANDARDS.md`** e **`AGENTS.md`**: ponteiros para o novo doc
  (Codex herda via AGENTS.md).

## Seção 4 — Contratos, docs e verificação

- **`CLAUDE.md`**: triagem por perfil (tabela curta), semântica do
  `ORCHESTRATOR_WRITE_ASK` (aprovar = implementar inline; recusar = delegar),
  exceção dura de fluxos sensíveis, política de exposição resumida.
- **`AGENTS.md`**: campo `Profile` documentado (Codex também respeita: em light,
  implementação inline na thread principal é aceitável para tarefas pequenas),
  rota de design (`DESIGN_STANDARDS.md`), gates proporcionais.
- **`USAGE.md` / `README.md`**: seções de perfis, nova política de `.env`, design.
- **`scripts/quality/hook-smoke.mjs`** — novos casos:
  1. standard + main + app code → ask; 2. light + main + app code → pass;
  3. governança → deny nos dois perfis; 4. `.env` ignorado → pass (Write e Bash);
  5. `.env` versionável → deny; 6. segredo em arquivo ignorado → pass;
  7. segredo em arquivo versionável → deny; 8. `git add -f` → ask;
  9. Profile ausente/corrompido → comporta como standard.
- **`starter-doctor.mjs`**: valida o valor de `Profile`; warn se inválido.
- **`VERSION`** → `1.1.0`; entrada no **`CHANGELOG.md`**;
  `update-from-template.mjs` cobre os arquivos novos (hooks/lib, rules, skills).

## Fora de escopo (YAGNI)
- Skill dedicada de design-review com screenshots (descartada na clarificação).
- Perfis adicionais (`assisted`, `strict`) — só `standard` e `light`.
- Relaxamento de governança em qualquer perfil.
- Mudanças no lado Codex além de documentação de contrato (hooks do Codex não mudam).

## Riscos e mitigação
- **Segredo em arquivo ignorado que depois é des-ignorado / `git add -f`** → `git add -f`
  vira ASK; quick-check continua bloqueando segredo em linha adicionada de diff no fim
  do turno; `.gitignore` é editável mas o diff dele é inspecionado pelo quality-gate.
- **`git check-ignore` custa ~10ms por chamada de hook** → aceitável (roda 1× por
  Write/Edit, só quando o alvo casa com os padrões).
- **Light virar default silencioso** → default do template é `standard`; light só via
  decisão explícita no onboarding ou edição manual do STACK.md.
- **Regressão nos hooks** → todos os comportamentos novos entram no `hook-smoke.mjs`
  antes do merge (TDD sobre os hooks).

## Execução
Implementação é **manutenção do template** (superfície de governança): sessão dedicada
com `CLAUDE_ORCHESTRATOR_WRITE_OVERRIDE=1` (cada escrita → ASK aprovado pelo humano)
ou fan-out para implementadores Sonnet com prompts de aprovação de governança. Plano
detalhado via `writing-plans` após aprovação desta spec.
